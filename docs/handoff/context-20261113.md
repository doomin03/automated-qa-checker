## 우선 원칙과 소유권

- Engine과 Checker는 독립 Git 저장소다. Engine은 다른 프로젝트에서도 공개 package API/CLI만으로 쓰며 Flutter/서버를 필수 의존하지 않는다. Checker는 React 사용자 웹, Flutter Desktop, Nest 서버와 생성 TS/Dart SDK의 모노레포다. npm registry 게시 완료를 뜻하지 않는다.
- 관리자는 계약·순서·인수·보존을 관리하고 제품 담당자는 자기 저장소만 수정한다. 모든 저장소 shell은 workdir를 명시하고 편집은 절대 경로로 한다. 기존 dirty/사용자 실행 앱/고정 package/과거 Release를 임의 삭제하거나 종료하지 않는다.
- Flutter는 feature-first MVVM + Provider다. View는 표시·UI 수명, VM은 상태·액션, Repository/Service는 파일/API/CLI를 담당하고 app composition root가 자원 소유와 dispose를 조립한다. ScreenUtil은 추가하지 않으며 제약 기반 배치·패널 접기·영역별 스크롤·사용자 text scale을 존중한다.
- 웹은 공용 시나리오 전달·진행·증거 조회 앱이다. 관리자 전용으로 좁히지 않는다. 업무 완료와 Engine PASS/FAIL, 실행 요청 ACK와 실제 terminal 결과를 분리한다.
- 제품 변경은 OpenSpec proposal/design/specs/tasks → strict → 관리 계약 검토 → apply → 실제 인수 순서다. Engine 기능은 고정 version/hash를 받은 뒤 소비한다. 완료 체크는 증거가 있을 때만 하고 미완료를 archive로 숨기지 않는다.
- 사용자/전역 Codex 설정·credentials는 임의 변경하지 않는다. AI 터미널은 기존 CLI 인증을 사용한다. 문서 수신·검증·AI 파일 수정은 자동 QA 실행이 아니며 앱의 실행 버튼은 불변 snapshot을 명시 실행한다.

기본 지침은 [AGENTS](../../AGENTS.md), [시스템 설계](../architecture/system-design.md), [Flutter MVVM](../architecture/flutter-mvvm.md), [모노레포 정책](../architecture/monorepo-policy.md)다. UI 작업은 `qa-workbench-design`과 `frontend-design` skill을 함께 읽는다. 최신 사용자 결정으로 재사용 문서 compose/template 변환은 Engine으로 이관됐으므로 skill의 오래된 Checker compiler 소유 문구보다 현재 공개 authoring 계약이 우선한다.

## 다른 PC에서 반드시 알아야 할 것

`artifacts/`, `.local/`, `build/`, `node_modules/`, 개발 SDK, 인증정보, ignored `desktop-installation.json`/`desktop-portable-runtime.json`은 **Git에 포함하지 않는다**. 따라서 clone만으로 위 EXE/실제 로그/패키지 archive가 생기지 않는다. 승인된 tgz와 해당 hash를 별도 배포 채널에서 확보하고 [설치 스크립트](../../scripts/install-desktop-engine.mjs), [portable 생성](../../scripts/prepare-portable-runtime.mjs), [전용 빌드](../../scripts/build-portable-desktop.mjs) 순서로 준비해야 한다. credentials나 개인 설정을 다른 PC로 복사하는 절차는 없다. 로컬 artifacts 상대경로는 원 담당 PC에서의 증거 위치 설명이지 Git 링크가 아니다.

주요 로컬 증거는 `artifacts/portable-runtime/acceptance.json`, `artifacts/runtime-alpha10/acceptance.json`, `artifacts/releases/desktop-portable-alpha10/{manifest,source-freeze,launch}.json`이다. 원래 별도 관리 폴더의 `remaining-implementation-20261112/management-review.md`와 `acceptance-matrix.md`에서 필요한 결정·수치·제약을 위 표로 흡수했다. 그 관리 폴더 없이도 이 문서와 저장소 내 OpenSpec로 다음 작업을 판단할 수 있다.

## 남은 조건과 다음 순서

1. readiness2.1: 실제 Codex XML/JSON 모델 편집→GUI→명시 실행 미인수. 기존 로그인 상태에서 허용된 한 번의 복구가 사용량 제한에 걸렸고 파일/config SHA 불변·owned PID 종료만 확인했다. 제한을 우회하거나 추가 모델을 임의 선택하지 않는다.
2. readiness2.2: Claude 미설치/실제 모델 미인수. 설치·인증 안내와 가이드 파일 준비를 실제 실행 성공으로 대체하지 않는다.
3. readiness2.3: 실제 Windows 한글 OS IME 미인수. widget 한글 입력과 focus 회귀를 OS IME 증거로 바꾸지 않는다.
4. A07 웹 관리 화면은 아직 구현 대상이다. 현재 관리 API/SDK를 소비해 역할별 UI를 구현하고 실제 HTTP/브라우저로 인수한다. [A07 tasks](../../openspec/changes/qa-persistent-project-administration/tasks.md)는 API 범위8/8이다.
5. [Registry lifecycle 초안](../../openspec/changes/qa-registry-review-lifecycle/proposal.md)을 검토·승인 후 초안 수정/반려/폐기를 구현한다. 게시 원본과 이미 실행 중인 결과 보고는 보존한다.
6. 그 다음 [개인 업무함 초안](../../openspec/changes/qa-assignment-inbox/proposal.md)을 확정해 QA/Suite 배정·수신·업무 완료를 Engine 결과와 분리한다. 현재 구현 인수가 없다.
7. fleet/외부 알림/locator 후보·Recorder/실제 Android·iOS·TV/whitebox는 별도 후속이다. Engine locator 명세만으로 구현 완료를 주장하지 않는다. 실제 계정·기기 없는 조건과 코드 미구현을 각각 기록한다.

재개 시 Git root/HEAD/dirty/원격 상태와 담당 파일 소유권부터 다시 확인한다. 최신 D08/portable를 재구현하지 않는다. 현재 checkpoint 승인은 저장 권한이며 추가 기능 계약이나 force push/이력 재작성 권한이 아니다. 기존 ahead CI commit의 workflow 권한 문제가 재발하면 실패 원인을 보고하고 임의 브랜치 우회·강제 push하지 않는다.
